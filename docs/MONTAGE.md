# Автоматический монтаж

## Зачем

До появления `montage.py` каждый клип рендерился как один непрерывный дубль: одна раскладка на весь клип, без ускорения пауз, без акцентов на пиках. Это оставляло на столе классические приёмы вертикального монтажа — вырезание "воды", punch-in на кульминации, жёсткое переключение раскладки на визуальное событие — которые заметно повышают удержание.

`montage.plan_edit` строит детерминированный план монтажа (`EditPlan`) — список кусков исходного клипа (`Cut`) с собственной раскладкой, зумом и скоростью для каждого. План строится один раз на клип и используется и рендером (для нарезки видео), и генератором субтитров (для пересчёта таймкодов слов) — см. [ARCHITECTURE.md](ARCHITECTURE.md#почему-план-монтажа-и-субтитры-строятся-вместе).

## Стадии планировщика (`montage.plan_edit`)

Выполняются строго по порядку, каждая — поверх результата предыдущей:

1. **Раскладка по времени (`_layout_segments`).** Клип нарезается на сегменты по границам `webcam_cut_time` и окна визуального события (`event_time`/`event_end`), с раскладкой для каждого сегмента (`split`/`webcam_full`/`gameplay_full`/`event_layout`). Границы сегментов "прилипают" к ближайшему пробелу между словами (`_snap_to_word_gap`), чтобы не резать посреди фразы.
2. **Вырезание пауз (`trim_silence`).** Ищутся паузы дольше `max_silence_seconds` вне защищённых зон (см. ниже), из каждой вырезается середина с отступом `silence_padding_seconds` от краёв. Суммарный объём вырезаний ограничен `max_removed_ratio`.
3. **Punch-in зумы (`punch_in`).** На самых громких аудиопиках (`props["peaks"]`) вставляется короткий зум (`punch_zoom` на `punch_seconds`), не чаще, чем раз в `punch_cooldown_seconds`, максимум `max_punches` раз за клип.
4. **Хук (`hook_punch`).** Лёгкий зум (`hook_zoom`) на первые `hook_seconds` клипа — усиливает первую секунду, где решается, долистает ли зритель дальше.
5. **Альтернатива вырезанию — ускорение (`speed_up_silence`).** Если включено вместо `trim_silence`, найденные паузы не вырезаются, а проигрываются с ускорением `silence_speed` — сохраняет полную последовательность действий ценой чуть более быстрого произношения пауз.

Если `montage.enabled: false` или входная длительность `<= 0`, вместо всего этого возвращается `passthrough_plan` — один `Cut` на весь клип без изменений.

## Ключи `montage.*`

Полная таблица с диапазонами — в [CONFIGURATION.md](CONFIGURATION.md#montage). Кратко, по функциональным группам:

| Группа | Ключи |
|---|---|
| Включение | `enabled` |
| Вырезание пауз | `trim_silence`, `max_silence_seconds`, `silence_padding_seconds`, `min_segment_seconds` |
| Ускорение вместо вырезания | `speed_up_silence`, `silence_speed` |
| Защита от чрезмерного монтажа | `protect_head_seconds`, `protect_tail_seconds`, `max_removed_ratio` |
| Раскладка события | `event_layout` |
| Punch-in | `punch_in`, `punch_zoom`, `punch_seconds`, `punch_cooldown_seconds`, `max_punches` |
| Хук | `hook_punch`, `hook_seconds`, `hook_zoom` |

Любой из этих ключей можно переопределить для конкретного шаблона через секцию `motion:` в YAML шаблона (см. [TEMPLATES.md](TEMPLATES.md)) — `montage._resolve_montage_config` сначала смотрит `template_motion`, затем `config["montage"]`, затем дефолт из кода.

## Защищённые зоны

Три типа регионов никогда не попадают под вырезание пауз (`_protected_regions`):

1. **Первые `protect_head_seconds` секунд** (по умолчанию 2.0) — хук клипа. Резать первую пару секунд рискованно: это ровно то время, за которое зритель решает, оставаться ли на видео.
2. **Последние `protect_tail_seconds` секунд** (по умолчанию 1.5) — развязка/punchline. Обрезка конца лишает клип кульминации, ради которой он вообще был выбран.
3. **Окно подтверждённого визуального события** (`event_time`/`event_end`, если `gameplay_event_validated: true`) — момент, который Gemini Vision явно нашёл и подтвердил по кадрам. Резать внутри него — риск случайно вырезать сам скример/клатч, ради которого клип попал в отбор.

Логика намеренно консервативна: если пауза хотя бы *частично* пересекается с защищённой зоной, она не режется целиком, а не обрезается частично (`_eligible_gap_middles`, `_overlaps`) — простая, но надёжная защита от попадания на секунду не в ту сторону.

## `max_removed_ratio`

Ограничивает суммарную долю длительности клипа, которую можно вырезать (по умолчанию 25%). Без этого ограничения агрессивный алгоритм вырезания пауз на клипе с длинными задумчивыми паузами мог бы срезать треть или больше исходного материала, превратив естественную речь в рубленый, неестественно быстрый монтаж. `_apply_ratio_budget` жадно принимает кандидатов на вырезание, пока не исчерпан бюджет `duration * max_removed_ratio`.

## Как читать `edit-plan.json`

Файл пишется рендером (`ffmpeg_render.render_with_ffmpeg`) в каталог клипа рядом с `remotion-props.json`. Структура — сериализация `EditPlan.to_dict()`:

```json
{
  "template": "classic-split",
  "plan": {
    "cuts": [
      {
        "source_start": 0.0,
        "source_end": 1.5,
        "layout": "split",
        "zoom": 1.06,
        "speed": 1.0,
        "reason": "hook"
      },
      {
        "source_start": 1.5,
        "source_end": 8.2,
        "layout": "split",
        "zoom": 1.0,
        "speed": 1.0,
        "reason": "body"
      }
    ],
    "source_duration": 42.3,
    "output_duration": 38.1,
    "removed_seconds": 4.2,
    "cut_count": 6
  }
}
```

Поля одного `Cut`:

| Поле | Значение |
|---|---|
| `source_start` / `source_end` | Границы куска в системе координат *исходного* (ещё не смонтированного) клипа, секунды |
| `layout` | `split` \| `webcam_full` \| `gameplay_full` — какую раскладку шаблона применить на этом куске |
| `zoom` | Дополнительный множитель зума поверх зума самой полосы шаблона (`1.0` — без изменений) |
| `speed` | Множитель скорости воспроизведения (`1.0` — обычная; `> 1.0` — только при `speed_up_silence`) |
| `reason` | `body` (обычный сегмент), `hook`, `punch`, или `silence-trim` — для отладки, откуда взялся этот кусок |

Общая длительность выходного видео — `output_duration` — всегда меньше или равна `source_duration` при вырезании пауз (`speed_up_silence: false`), либо равна при ускорении (изменяется только скорость проигрывания внутри кусков).

## Трекинг лица

### Зачем

До появления `face_tracking.py` кроп вебки центрировался на **геометрическом центре** заранее заданного или визуально найденного bounding box вебки — не на самом лице внутри него. Для статичной, всегда одинаково расположенной вебки это работало нормально. Но как только полоса вебки в шаблоне становится узкой (например, `gameplay-focus` с 26% высоты) или лицо стримера смещено внутри рамки камеры (стример откинулся, повернулся, встал), геометрический центр бокса и реальное положение лица расходятся — в крупных сценах лицо могло уехать из кадра целиком.

### Как работает

`face_tracking.track_face`:

1. **Детекция.** YuNet (`cv2.FaceDetectorYN`, ONNX-модель `face_detection_yunet_2023mar.onnx`) применяется к кадрам, извлечённым ffmpeg с частотой `sample_fps` (по умолчанию 4 кадра/сек — трекинг не требует полного FPS, лицо не двигается рывками между соседними видеокадрами).
2. **Выбор доминантного лица.** Если в кадре несколько лиц (стример + друг в гостях, лицо на фоновом видео), `_select_dominant_track` группирует детекции в треки по близости (центр/IoU) и выбирает самый устойчивый и крупный — не первый попавшийся.
3. **Сглаживание в четыре прохода (`smooth_samples`):**
   - **Median (`median_window`)** — убирает единичные выбросы детектора (ложное срабатывание на один кадр);
   - **Deadband (`deadband`)** — игнорирует микро-дрожание меньше порога, чтобы кроп не подёргивался на статичном лице;
   - **EMA (`ema_alpha`)** — экспоненциальное сглаживание, делает движение плавным;
   - **Ограничение скорости (`max_velocity`)** — не даёт кропу "прыгать" быстрее физически правдоподобного движения головы, даже если детектор внезапно перескочил на другую точку.
4. **Интерполяция между сэмплами.** `FaceTrack.bbox_at(time)` линейно интерполирует между соседними сэмплами; разрыв длиннее `max_gap_seconds` не интерполируется (лицо явно пропадало из кадра надолго).

### Ключи `face_tracking.*`

Полная таблица — в [CONFIGURATION.md](CONFIGURATION.md#face_tracking).

### Как отключить

Глобально — `face_tracking.enabled: false` в конфиге. Для одного прогона — флаг `--no-face` у `tools/render_probe.py`. При отключении крoп полностью возвращается к геометрии `align_x`/`align_y` шаблона и статичным координатам вебки из `layoutRecommendation`/`config["layout"]`.

### Деградация при неудачном трекинге

Трекинг — стадия обогащения, а не обязательная. Три независимых уровня отказоустойчивости (`ffmpeg_render.resolve_face_track`):

1. Если OpenCV не установлен или ONNX-модель не найдена на диске — трекинг тихо пропускается (`_empty_track`), лог-уровень `warning`.
2. Если сама детекция бросает исключение (повреждённый файл, сбой ffmpeg-пайпа) — перехватывается, лог с полным traceback, крoп остаётся на конфигурационной геометрии.
3. Если лица в заданном боксе вебки нет, а `face_tracking.search_full_frame` включён, делается вторая попытка по всему кадру. `layout.webcam` — догадка под конкретного стримера, и на чужом канале он легко указывает в пустой угол. Замер на реальном клипе: в боксе из конфига `coverage=0.09`, по всему кадру — `0.87`. Если вторая попытка удалась, кроп строится по найденному лицу, а в журнал идёт `WARNING` с координатами — по нему нужно починить конфиг, а не жить на страховке.
4. Если трекинг технически отработал, но **покрытие** (`coverage` — доля кадров с найденным лицом) ниже `face_tracking.min_coverage` (по умолчанию `0.4`) — трек считается ненадёжным (`FaceTrack.is_usable`) и отбрасывается целиком, даже если часть трека была качественной. Частичный, дырявый трек хуже, чем его отсутствие: лучше стабильный кроп по конфигурационной геометрии, чем кроп, скачущий между настоящим треком лица и провалами в нём.

## Как посмотреть результат: `tools/render_probe.py`

Скрипт рендерит один клип с явными переопределениями и печатает принятые решения по кадрированию — правка композиции не может быть проверена чтением filtergraph, только реальным рендером и взглядом на результат.

```bash
PYTHONPATH=src python3 tools/render_probe.py \
    --source remotion/public/jobs/<job>/clip-02/source.mp4 \
    --out .work/probe/after --template classic-split
```

Флаги:

| Флаг | Назначение |
|---|---|
| `--source` (обязателен) | Путь к исходному видео для пробного рендера |
| `--out` (обязателен) | Каталог результата (пересоздаётся с нуля при каждом запуске) |
| `--config` | Конфиг (по умолчанию `config/default.yaml`) |
| `--template` | Имя шаблона (переопределяет `render.template` из конфига) |
| `--layout` | Раскладка для теста: `split` (по умолчанию), `webcam_full`, `gameplay_full` |
| `--webcam` | Ручное переопределение области вебки: `x,y,w,h` в диапазоне 0..1 (например, `0,0,1,1` для полнокадровой вебки) |
| `--no-face` | Отключить трекинг лица для этого прогона |
| `--no-montage` | Отключить монтажный план (принудительный `passthrough`) |
| `--stills N` | Сколько равномерно распределённых стоп-кадров сохранить (по умолчанию 4) |

После рендера скрипт печатает имя использованного шаблона, длительность до/после монтажа, полный список кусков плана (`source_start`/`source_end`/`layout`/`zoom`/`speed`/`reason`) и сохраняет стоп-кадры `still-*.png` в каталог результата — смотреть их и есть единственный надёжный способ оценить композицию.

## Ограничение: `MAX_FOCUS_KEYFRAMES`

Траектория движения кропа (будь то трек лица или траектория визуального события) транслируется в FFmpeg-выражение `crop=...:x=...:y=...` с вложенными `if()` на каждую ключевую точку (`tracking.PointTracker`). У парсера выражений FFmpeg есть практический потолок сложности: трек лица с частотой 4 сэмпла/сек на 30-секундном клипе — это уже 126 точек, что на практике давало выражение на ~18 КБ, которое FFmpeg отказывался принимать вообще (`crop` filter не конфигурировался).

Поэтому перед тем, как трек попадает в filtergraph, он прогоняется через `_simplify_trajectory` — упрощение траектории (аналог Ramer–Douglas–Peucker: жадное удаление точки, чей пропуск при линейной интерполяции меняет путь меньше всего), пока не останется не больше `MAX_FOCUS_KEYFRAMES = 24` точек или пока каждая оставшаяся точка не будет значимой (отклонение больше `FOCUS_TOLERANCE = 0.004`, в долях кадра). Гладкое движение камеры физически не нуждается в такой плотности ключевых точек, как исходный трек, — 24 точки на клип оказывается достаточно, чтобы движение выглядело плавным.

Практическое следствие: если вы видите, что трекинг лица работал (`coverage` высокий в `face-track.json`), но итоговое движение кропа выглядит чуть менее отзывчивым, чем сырой трек — это ожидаемо, а не баг.
